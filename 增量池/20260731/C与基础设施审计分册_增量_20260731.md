## ① 新漏洞特性与漏洞模式演变

### 1-1 NGINX map 指令 15 年潜伏堆溢出（CVE-2026-42533）：“两遍求值信任自己的测量”【窗口内 · 本期重点】

- **时间**：2026-07-15 F5 公告 K000162097；07-19 ～ 07-27 中英文深度分析集中发布；CVSS v3.1 8.1 / v4.0 9.2
- **模式提炼（设计级缺陷）**：
  - NGINX 脚本引擎拼接字符串采用**两遍求值**：第一遍 LEN 测量所需缓冲区长度，第二遍 VALUE 写入；两遍共享 PCRE 捕获数组（`$1`、`$2` …）；
  - 当配置为“正则 `map` 的输出变量在字符串表达式中被引用，且引用点**晚于**前序正则捕获（如 location 正则的 `$1`）”时，`map` 正则的执行夹在两遍之间**覆写共享捕获状态**：LEN 遍按原捕获测量，VALUE 遍按攻击者可控的新捕获写入——长度与内容双双失配 → 堆缓冲区溢出；
  - 反向情形（新捕获更短）则返回**未初始化堆数据**：研究者验证默认 Ubuntu 24.04 上单条未认证 GET 即可泄露堆/libc 指针，**等于自带 ASLR 绕过**，实验室利用成功率 10/10；
  - 漏洞自 2011-03（0.9.6 引入 map 正则支持）存在约 15 年；预认证、无交互、单请求触发；修复版本 1.30.4 / 1.31.3 / Plus 37.0.3.1。
- **同根因家族（重要趋势）**：这是约两个月内表达式求值代码的**第三个堆溢出**——CVE-2026-42945（Rift，5 月，map 求值陈旧标志，已被在野利用）、CVE-2026-9256（6 月，rewrite 模块捕获重叠）、CVE-2026-42533（7 月）。**“两遍求值器信任自身测量结果”这一架构假设在功能演进后失效**，是基础组件中典型的潜伏型设计缺陷。
- **审计要点**：
  - 代码审计：凡是“先测量后写入”的两遍式实现，检查两遍之间是否所有共享可变状态（正则捕获、缓存标志、迭代器）都被快照/隔离；
  - 配置审计：排查“正则捕获源（location/server_name/rewrite 带括号）与正则 map 变量同表达式混用”的排序模式；临时缓解（命名捕获改写）不完整——map 复用 location 同名命名组仍可经第二路径触发，**升级是唯一完整修复**；
  - 检测：worker SIGSEGV/SIGABRT 崩溃、指向正则 map 端点的异常长 URI/参数。
- **来源**：F5 公告转述与 Stan Shaw 研究、The Hacker News、friday-go.icu 攻击链分析、代码卫士编译（参考 1-4）

### 1-2 Redis 认证后 RCE 双漏洞公开 PoC（CVE-2026-25589 等）【窗口内】

- **时间**：2026-07-25 中文预警与 PoC 要点公开（注明：细节来源为单一社群文章，建议交叉核实官方公告）
- **模式提炼**：
  - 其一：Stream consumer-group 共享 NACK（否定确认）路径的**双重释放（double free）**，影响 6.2.22 ～ 8.8.0 全版本区间；
  - 其二：RedisBloom 模块 **TDigest 堆溢出**；
  - 认证后触发、攻击复杂度低；暴露面数据：全球约 72 万 Redis 实例公网可见，其中约三千余个无密码直连（认证后门槛对这批实例等同未认证）。
- **审计要点**：
  - C 代码审计关注“共享结构体的销毁路径”：同一对象被两个逻辑所有者各释放一次是 Redis 这类长生命周期服务的高发模式；
  - 模块体系（RedisBloom 等）与核心分开评估：第三方模块的解析器（TDigest、布隆过滤器参数解析）是堆溢出富矿区；
  - 部署基线：不出公网、强密码 + ACL、模块最小化加载。
- **来源**：爱坤sec《Redis 认证RCE PoC 公开》（经 7/25 精选总览收录，参考 5）

### 1-3 微软 7 月补丁日：622 枚漏洞、Windows 内核 EoP 集群【窗口内】

- **时间**：2026-07-14/15
- **模式提炼**：
  - 单月 622 枚创纪录，其中 Windows 416 枚（去年同期约 137）；Win32k 一族 EoP 集中出现（7.8 ～ 8.8 分多枚）、srvnet.sys RCE、BitLocker 物理绕过等；
  - 数量暴涨背景：厂商与研究方普遍归因于 **AI 辅助审计/挖掘规模化**（见综合分册），漏洞产出曲线整体抬升；
  - 防御含义：补丁吞吐能力成为瓶颈，“月度 CSPU 式”高频补丁机制在微软/Oracle 双侧同时出现。
- **审计要点**（Windows 内核研究方向）：Win32k 仍是 EoP 富矿，关注句柄/对象引用计数与 GDI 对象生命周期类模式；驱动层关注 IOCTL 输入校验与双重获取（double fetch）。
- **来源**：ZOL 快讯、Rapid7/ZDI 补丁日评述（参考 6-8）

## ③ 审计思路与 CTF 技巧

### 3-1 内核 CTF 技巧动向：eBPF 验证器与 per-CPU 栈 Pivot【月初回溯】

- **时间**：2026 上半年赛事 writeup 汇总（7 月持续被引用）
- **技巧提炼**：
  - **eBPF variable-shift range confusion**（UofTCTF 2026）：验证器对可变移位运算的范围推导与运行时实际值不一致 → map value 越界读写 → `modprobe_path` 覆写提权；审计/出题关注点：验证器对 ALU 操作的抽象解释精度；
  - **per-CPU 栈指针破坏 + 栈 pivot**（TRX CTF 2026 高分题）：污染 per-CPU 栈指针后以 FSGSBASE/SWAPGS 完成栈迁移——内核利用原语向“破坏每核私有状态”演进，绕过传统全局对象覆写检测；
  - 经典路径仍然有效：kmalloc UAF + 竞争、`commit_creds(&init_cred)`、dirty pagetable。
- **审计要点**：内核/eBPF 审计优先验证“验证器静态范围 vs 运行时可达值”的一致性；利用侧关注 per-CPU 数据结构的破坏价值。
- **来源**：Kernel-Exploit-Dojo 汇总仓（参考 9）
